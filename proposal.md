Wazuh only sees what its ruleset knows how to interpret. An event that matches no decoder and no rule generates no alert, no error, and no trace. It is absorbed silently.

The operational problem is that "nothing bad is happening" and "nothing is looking" produces identical silence. There is no view in Wazuh that says "15% of your event patterns are unparsed."

I built a tool that measures this continuously, and — optionally — drafts the missing decoder and rule for human review. 




Implementation: Python package + SQLite + cron


archives.log  (2.9M events/day)
   │ 1. normalise → fingerprint the pattern, not the log line
   ▼
64,562 unique patterns
   │ 2. threshold — 95% appear once or twice; that tail is discarded
   ▼
~1,300 candidates
   │ 3. wazuh-logtest → decoder? rule? what level?
   ▼
119 patterns with no recorded decision
   │ 4. (optional) LLM drafts decoder + rule
   ▼
human approves or decline → validated write → manager restart


LLM interaction:

On the LLM. It receives the sample logs, the pattern, the occurrence count and the inventory of existing decoder names, and returns strict JSON: is this worth monitoring, at what level, and the proposed decoder/rule XML. It never writes files, never chooses its own rule IDs, never applies anything



I have attached screenshots of the dashboard showing the unmanaged logs, as well as the table where you can either reject a log (if it isn't worth storing) or approve it (if you believe it makes sense for your environment).


This way, when we add a new device that lacks official rules and decoders, we can rest assured that the correct logs are being monitored; this facilitates the implementation of decoders and rules generated by an LLM (along with their verification via `wazuh-logtest`).
